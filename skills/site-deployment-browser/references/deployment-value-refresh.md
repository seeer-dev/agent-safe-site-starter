# Deployment value refresh — reusable operator worksheet

This reference applies to each installation of this single-site starter. Replace angle-bracket placeholders with values observed **in that installation's current dashboard**; never copy another site's IDs, URLs, branch, token name, user, or email. Record actual non-secret values and results in installation-specific deployment documentation, not this skill. The holder enters secrets directly in provider dashboards. No `.env.production`.

## Operator worksheet

Record `<owner/repo>`, chosen release branch `<branch>`, remote ref/commit, selected Railway account/workspace/project/environment/service, actual GitHub source/deployment commit and public HTTPS origin `https://<railway-origin>`, storefront `https://<storefront>.pages.dev`, admin `https://<admin>.pages.dev`, Supabase project, R2 bucket/public origin, and chosen Resend domain. `git ls-remote --heads origin <branch>` verifies the source. Pages and Railway select branches independently. If Railway's picker fails, inspect GitHub App repo scope and project-member/contributor account before changing access. A source label or staged variable is not live until applied and deployed from GitHub.

Ask for login/MFA handoff. Follow action-time confirmation for production mutation, credential creation, DNS, mail send, owner promotion, and test data. Never inspect revealed values or take secret-bearing screenshots. Label each item `absent`, `staged`, `live`, or `proved`. Stop before release if database/edge values are absent, the selected Railway service is uncertain, or Cloudflare secret-classified rows are `Text／文字`.

Cloudflare `Secret／秘密` is encrypted; `Text／文字` is not. The Variables page can include the **literal value** of a Text row in an automatic accessibility/DOM observation. For a type audit, use a tool path that returns only name/type and suppresses the full value-bearing output; if unavailable, let the holder inspect the type and report only `Text` or `Secret`. Never click “show,” copy, or print the row. If a database URI or edge credential appears as Text, holder rotates it, removes the Text row, enters a **new** credential as Secret at every destination, redeploys, and repeats proof. **Do not put an exposed old edge value into `EDGE_SECRET_PREVIOUS`.** For a *planned rotation of an uncompromised value* only: Railway accepts new `EDGE_SECRET` and old `EDGE_SECRET_PREVIOUS` briefly, deploy; update/redeploy both Pages; prove endpoints; remove previous and redeploy Railway.

### Sources → destinations

| Source | Value | Destination and type |
|---|---|---|

Never admin/browser. |
| Supabase **Connect** or **Settings → API Keys** | Project URL and **Publishable key**, not a service-role key. | `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` public Text on Railway and both Pages build environments. |
| Holder's secret manager/generator | One fresh high-entropy edge credential. | `EDGE_SECRET`: Railway Secret, storefront Pages **Production Function Secret**, admin Pages **Production Function Secret**; holder enters the same value directly in all three. |
| Selected Railway service → **Settings → Networking / Domains** | Active **public HTTPS** origin, no trailing slash; never `railway.internal`. | `API_ORIGIN` Text in **each** Pages project's Production Function environment. |
| Cloudflare **Workers & Pages** → each project's production deployment/domain | Actual `https://<storefront>.pages.dev` and `https://<admin>.pages.dev`. | Storefront URL to Railway `SITE_ORIGIN`, `PUBLIC_SITE_URL`, `PUBLIC_API_BASE` and storefront build `PUBLIC_SITE_URL`/`PUBLIC_API_BASE`. Admin URL is the exact R2 CORS origin. |

This backend is a persistent Go process with a bounded PostgreSQL pool. **Session pooler** is the IPv4-safe default. Direct needs verified Railway outbound IPv6 or a Supabase IPv4 option. Transaction pooler is a deliberately changed short-lived-runtime exception, potentially requiring simple protocol. `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` are not a database connection.

| `R2_PUBLIC_BASE_URL` | Bucket → **設定（Settings） → 公用開發 URL（Public Development URL） → 啟用（Enable）** for test; **自訂網域（Custom Domains） → 新增（Add）** for production | Railway Text + storefront Pages Production **build** Text; actual URL without trailing slash. `r2.dev` is temporary. |

Bucket **設定（Settings） → CORS 原則（CORS policy）** must allow only the actual admin Pages origin, `PUT`, and `Content-Type`:

```json
[
  {
    "AllowedOrigins": ["https://<admin>.pages.dev"],
    "AllowedMethods": ["PUT"],
    "AllowedHeaders": ["Content-Type"]
  }
]
```

Browser requests a short-lived presigned upload from authenticated Go API, directly PUTs bytes to R2, then requests API verification. No R2 credential enters browser. Deploy Railway after CORS/values, add public URL only to storefront build, deploy storefront. Prove presign → PUT → verify → `verified/product-images/` key → product-image association → public image fetch with loaded dimensions. Bucket/token/public URL alone are not proof. `R2 is not configured`: check four runtime names and fresh Railway deployment. Preflight fail: exact CORS. Image 404: verified key, association, public URL, fresh storefront build. If presign says the extension disagrees with `Content-Type`, inspect file magic, extension, and browser MIME before changing credentials: a `.png`-named JPEG is not a valid PNG upload. Make a disposable `.jpg` copy of non-sensitive JPEG bytes for the smoke test and upload that copy; leave the original source unchanged and do not relax API validation. Do not log presigned URLs or full verified object keys.

## Resend 交易信 / email

An owned sending domain/subdomain is required; `*.pages.dev` cannot supply its DNS. Account display label is not proof of ownership. Ask owner to choose a DNS-controlled sender domain.

1. Resend **網域（Domains） → 新增網域（Add Domain）**; open chosen domain detail and use its **currently generated** records, not copied examples.
2. Cloudflare **網站（Websites） → chosen zone → DNS → 記錄（Records） → 新增記錄（Add record）**; enter Resend-provided SPF/DKIM/return-path rows exactly. For CNAME choose **僅 DNS（DNS only）**, not proxy. DNS changes or Resend's optional **Sign in to Cloudflare** Domain Connect need current authorization. Click **Verify DNS Records** and wait for **Verified**.
3. Resend **API Keys → Create API Key**; choose **Sending access** restricted to verified domain when offered. Holder takes one-time key directly to Railway `RESEND_API_KEY` **Secret**. `RESEND_FROM` Railway Text must use that exact verified domain; holder sets `CONTACT_NOTIFY_TO` as Railway protected recipient. No Resend values in Pages.
4. Deploy Railway, check health. With separate current permission and an explicitly identified owner-controlled recipient, perform **one** labeled mail test; inspect Resend **Emails/Logs** for `sent` or `delivered` and ask the holder to check inbox and spam for the unique marker. A `201` contact response confirms persistence and a successful return from the configured sender, but a blank API key silently selects the local log sender, and `sent` is not inbox proof. If the holder reports the matching message in spam, record mailbox arrival plus spam placement separately; do not claim normal-inbox deliverability. If the dashboard cannot be read, record owner-observed arrival but keep provider-event proof pending. Contact path persists `contact_inquiries` before send: inspect before retrying a failed POST to avoid duplicates. Commerce notification goes to order/customer email, not `CONTACT_NOTIFY_TO`; an order test needs separate authorization.

Resend 401: holder checks Railway key/deployment. 403/domain mismatch: compare `RESEND_FROM` and restricted key scope. Railway healthy with no Resend event: event/key may not be live. Never reveal key or private recipient.

If an authorized message reaches spam despite Resend **Delivered**, open **Emails → that message → Insights**. Record only the warning category, not recipient or message content; ask the holder for the inbox provider's spam-reason text and SPF/DKIM/DMARC pass/fail summary, not the full private headers. A verified Resend domain confirms its SPF/DKIM setup, but it does not establish a DMARC policy or guarantee inbox placement. Check the **actual `RESEND_FROM` domain** for exactly one valid `_dmarc` TXT in public DNS and the authoritative Cloudflare zone. If missing, the least disruptive first policy is `v=DMARC1; p=none;` at `_dmarc` (TTL Auto); it is monitoring-only and can apply to the organizational domain's subdomains. Add `rua` only after the holder chooses a real report destination. Never select `quarantine`/`reject` before checking all legitimate mail sources. Obtain explicit action-time authorization **before saving DNS**; an unsaved form or local documentation edit is not publication. After saving, check public DNS and Resend's refreshed analysis, then request separate permission and a confirmed recipient for a single new mail test. Inspect its `dmarc=pass` result and inbox/spam separately. A previous message or cached Insights report will not retroactively prove the new record. Do not promise that DMARC alone resolves spam filtering or modify working mail code without a code-level cause.

For a mail-authentication fix, use the selected sending domain's **Websites → DNS → Records**, not **R2 → Manage API Tokens**. R2 access keys are for object storage and must not be changed to address email placement. A DNS-only TXT publication needs public-DNS verification, not a Railway or Pages redeployment; a new message is needed to evaluate the changed authentication state.

On a fresh post-publication message, Resend **Insights → Include valid DMARC record** moving into **Doing great** confirms that its analysis detected the DNS policy. It is not the receiving mailbox's `dmarc=pass` verdict or proof of inbox placement. Keep the Resend `Delivered` event, the receiver's SPF/DKIM/DMARC authentication summary, and inbox-versus-spam observation as separate evidence; never resend a persisted inquiry just to refresh an old report. If a later order notification and contact test both reach spam after the policy change, mark both mailbox arrivals and the unresolved placement issue without assuming the same cause or changing credentials, DNS policy, or template content from that observation alone. Ask for redacted receiver authentication verdicts and spam reason before proposing a further deliverability change; an order email should not be resent merely to investigate placement.

## Checkout readiness and no-payment test

Before claiming the admin-to-checkout-to-order loop, read the live storefront `GET /api/storefront/bootstrap` and `GET /api/payment-methods`. `data.shipping_methods` and `data.payment_methods` are independent: shipping being available does not imply checkout can finish. The Vue checkout requires a payment choice; Go `Quote` and `CreateOrder` reject a missing, disabled, or not-ready payment method. An empty public list is a configuration blocker, not permission to bypass validation.

The admin **商店（Store）→ 付款方式（Payment methods）** resource edits existing rows; an empty table has no create action. Ask the owner which **offline/no-gateway** option is appropriate before creating or enabling any method through an authorized admin/data path. A ready enabled method becomes visible on the public test URL; do not label a real cash-on-delivery obligation as a harmless simulation. Never copy an admin bearer token or database credential into a script or document to work around an empty UI.

For an owner-authorized *test-only* offline method when that admin table is empty: in the installation's Supabase project open **SQL Editor／SQL 編輯器 → New query／新增查詢**, confirm the selected project and **Primary Database／主要資料庫** first. Query only `id, method, provider_label, environment, readiness_status, enabled, fee` from `public.payment_methods`; do not dump orders, staff, or provider credentials. If an appropriate row exists, use the normal admin edit form instead. If there are no rows, obtain action-time approval for a publicly visible unpaid test option, then insert **one** collision-checked row using the actual schema: unique non-secret ID and `method=manual_test`, `provider_label=測試用人工付款（不請款）`, `environment=sandbox`, `readiness_status=ready`, `enabled=true`, `fee=0`, `updated_unix` current Unix seconds. Prefer `INSERT … SELECT … WHERE NOT EXISTS (…) RETURNING` to avoid a second row after a retry; inspect the returned row, not just the SQL success banner. A `manual_test` method is treated as configuration-only by this Go runtime; it does not call a gateway. Recheck storefront Pages `GET /api/payment-methods` and bootstrap; both must expose the method exactly once. No Railway/Pages redeployment is needed for a DB-only row. If the customer-facing page still advertises other unsupported payment types in static copy, note that separately; a single test method does not prove those claims.

Before order creation, record the labeled test product's stock and sold count without copying customer records. A side-effect-free `POST /api/quote` with one product SKU/quantity, an actual available shipping ID, and `payment_method=manual_test` must return the server total and `payment_fee=0`. A quote is not an order. If this run includes order email, check the selected database's `notification_templates` metadata (`code`, `is_enabled`, and nonempty subject/body booleans) **before** checkout. The development seed creates templates only in development; a new production database may have none. With separate approval of the message content and customer-facing notification, create exactly one truthful enabled `order_placed` template in authenticated admin **通知（Notifications）→ 通知模板（Notification templates）→ 新增（Create）**. An ordinary customer-facing template need not say "test", but should say that the order was received and its amount, refer to the authoritative payment/shipping status, and avoid claiming payment or shipment. Use only supported placeholders (`{{customer_name}}`, `{{order_id}}`, `{{total}}`); do not copy the development seed's premature shipping promise. Enabling the template affects all future order recipients, not only the owner's test mailbox. Read back the unique `order_placed` row and enabled state without logging a recipient or rendered message. The template is live DB configuration and needs no Railway/Pages redeploy.

The holder uses the visible storefront to enter **their own controlled** name, mobile, email, and legitimate test delivery details; add one unique `buyer_note` marker such as `DEPLOYMENT_ORDER_SMOKE_<date>_<nonce>`. The agent must not fabricate another person's address or ask for these values in chat. After the holder presses submit **once**, identify the result by marker (or the holder-controlled order page if note omitted) and verify only non-sensitive order status, payment status `unpaid`, method, quantity, total, stock delta, and notification status in authorized admin/SQL views. A latest-order query alone is not an identity proof when other orders could have arrived; corroborate its count/time with the holder's order page, and if accessible compare the provider subject to that exact order ID **in memory without printing or saving it**. Do not print order access tokens, full IDs, names, addresses, phone numbers, or email recipients. If the page times out, check the order list before any retry; the browser generates a new idempotency key per checkout view. If `notification_logs` says `skipped` with `template not found`, creating a template later **does not retroactively send**. The current admin **通知日誌（Notification logs）→ 重試（Retry）** copies the original rendered subject/body; when the original skipped row has empty content, retry only creates another skipped row. Do not click it or forge a log. A second order and additional stock effect require specific holder authorization, controlled destination, and fresh submission; the first order remains real and unpaid. For the new order distinguish the application's `sent:mail`, Resend `Delivered`, and recipient inbox-versus-spam observation as three different claims. Do not convert `unpaid` to paid, fulfill, or cancel/restock without a distinct decision. Keep the publicly enabled option visibly labeled as a test and decide whether to disable it before a real launch.

Creating an order persists personal fields, decrements stock transactionally, and dispatches a best-effort `order_placed` notification after commit; a failed email does not undo the order. Cancellation and restock are separate governed operations, not automatic cleanup. Stop before payment launch, fulfillment, or another order unless individually authorized. If the owner only approved a checkout-first-step smoke, label it partial rather than full commerce proof.

## Test-URL deployment and acceptance

1. Confirm the exact Railway project/environment/service and staged change count before the authorized **Apply changes → Deploy** action. Wait for the *new* GitHub-sourced deployment from the chosen branch to become `ACTIVE`/`Deployment successful` (not just the preceding still-online deployment), then check public HTTPS `/healthz`. In **Workers & Pages → each Pages project → Deployments／部署 → All deployments**, select the most recent successful **Production** row for the chosen branch/commit → **More actions／更多操作 → Retry deployment／重試部署**. Do this separately for storefront and admin **after** Production variables are saved; confirm each retry shows the expected branch/commit and `success` before testing the stable `.pages.dev` URL. Do not retry a Preview row or roll back to an older commit. Record the three new deployment IDs in the installation ledger, never in this skill.
2. Four independent requests *after both retries succeed*: `GET <railway-origin>/healthz` = 200; uncredentialed `GET <railway-origin>/api/products` = 403; `GET <storefront-pages-url>/api/products` = 200; `GET <admin-pages-url>/api/products` = 200. Direct 200 may mean no guard; Pages 403 means mismatch/old edge **or a still-running retry**; 502 suggests origin; 500 suggests database/migration. Never remove guard to make test pass. A build-success signal proves the new deployment, not R2 key validity, mail delivery, or a production-domain release.
3. Supabase **Authentication → Users** gives exact Auth UID. Go API requires matching `public.staff_members.supabase_user_id` with `status=active` and `role_label=owner` for first-owner controls. Request current authorization before provisioning; never match email. Prove role in a fresh admin session.
4. Publish labeled active product; wait for hydrated storefront live catalog/API rather than older static fallback. Cart → checkout first step without contact/order/payment. Static/SEO fallback needs separate repository render/publish/deploy.
5. Prove R2 image upload, association, public fetch; independently prove one authorized Resend event. Before contact POST, obtain explicit confirmation of the actual owner-controlled `CONTACT_NOTIFY_TO` recipient; do not infer it from a variable name, open a secret row, or use a different path to bypass a denied external send. A failed send may still persist the inquiry, so inspect events/inquiries before any retry. Admin deep link must load without an invalid Pages redirect warning after source release. Payment and custom domains remain outside this test unless requested.

Report a matrix of branch/deployment, database/edge, admin, product/cart, R2, mail, and deep link as `absent/staged/live/proved` with timestamp. Do not call the loop complete when only proxy/product smoke passed. Link actual `pages.dev` test URLs in installation-specific docs, not this reusable skill.

For a later production-domain cutover, bind owner-chosen site/admin domains to their respective Pages projects and a custom image domain to R2, await HTTPS, update Railway `SITE_ORIGIN`/`PUBLIC_SITE_URL`/`PUBLIC_API_BASE` and storefront build URLs, update exact R2 admin-origin CORS, redeploy all affected layers, then repeat proxy, role, commerce, media, and mail checks at the new URLs. If Railway's origin also changes, update both Pages `API_ORIGIN` values and redeploy them. Keep the verified mail sender/domain unless the owner explicitly changes it. Preserve the last known working test deployment as a rollback reference; ECPay/payment release needs separate configuration and proof.
