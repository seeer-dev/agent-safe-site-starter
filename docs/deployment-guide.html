Supabase PostgreSQL + Auth

申請 / 控制台

supabase.com/dashboard → 用 GitHub 登入即可，New Project 建一個專案（Region 選 Singapore 離台灣最近）。

要蒐集的資訊

三個值都在同一個地方拿：專案頁面右上角的「Connect」按鈕，點開的對話框裡有 connection strings 與 API keys。Keys 也可走左側 Settings → API Keys 獨立頁。

值在哪裡拿設到
DATABASE_URLSECRET Connect → Type 選 postgres（或 URI）→ Transaction pooler 分頁那串 aws-*.pooler.supabase.com:6543，[YOUR-PASSWORD] 換成建專案時設的 DB password。長得像 postgresql://postgres.xxxx:[密碼]@aws-0-ap-southeast-1.pooler.supabase.com:6543/postgres Railway + Pages build
SUPABASE_URL Connect → App Frameworks 分頁顯示的 https://xxxx.supabase.co；或 Settings → API 頁的 Project URL Railway + Pages + browser
SUPABASE_PUBLISHABLE_KEY Connect 同對話框的 sb_publishable_...；或 Settings → API Keys → Publishable key（不是 eyJ... 開頭的 legacy anon key） Railway + Pages + browser
Transaction pooler 必加參數：若用 pooler（port 6543）字串，尾端要加 &default_query_exec_mode=simple_protocol — pgx 的 prepared statement 在 transaction 模式下需要它。用 direct connection（port 5432）則不用。

建管理員帳號

  • Authentication → Users → Add user → Create new user，填後台登入用的 email + 密碼。
  • 若要 Google / LINE 登入：Authentication → Sign In / Providers 開啟，OAuth client secret 設在 Supabase 後台（不是環境變數）。

Data API / RLS 開關（重要）

本架構是「瀏覽器 → Go API → Postgres」，沒有任何東西走 Supabase Data API（PostgREST REST API）。Go 後端用 DATABASE_URL 直連 postgres 協定；Supabase Auth（JWT 驗證）是獨立服務，不受這些開關影響。

開關（Project Settings → Data API）建議理由
Enable Data API關 整站不走 /rest/v1/，關掉直接消掉整面攻擊面
Automatically expose new tables關 自動對 anon/authenticated 授權新表 — migration 一建表就對外暴露，永遠手動控管
Enable automatic RLS開 防禦縱深：新表自動啟 RLS，誤開 Data API 時預設 deny-all。對 Go 後端無副作用（postgres 角色 bypass RLS）

Cloudflare Pages 前台 + 後台

前台專案

Workers & Pages → Create → Pages → Connect to Git → 選 repo 與分支。

設定值
Build commandmake site（會照 SITE_THEME 建對的 theme bundle 再 render）
Output directorydist
環境變數APP_ENV=production、SITE_THEME=curatory、PUBLIC_SITE_URL=https://你的網域、PUBLIC_API_BASE=https://你的網域、R2_PUBLIC_BASE_URL、DB_DRIVER=postgres、DATABASE_URLSECRET（render 需要讀 DB）、Supabase 三件（AUTH_MODE/SUPABASE_URL/SUPABASE_PUBLISHABLE_KEY，這三個會進 browser bundle — 是公開值）
Functions 環境變數（兩個專案都要設）：Pages 專案 → Settings → Variables and Secrets → Add（不是 build 變數）→ API_ORIGIN = Railway 的 https://xxx.up.railway.app、EDGE_SECRETSECRET = 跟 Railway 同值。保存後重新部署，設定才會進入 Function。repo 根的 functions/api/[[path]].js 會攔截 /api/*、注入 secret 後轉發 — 瀏覽器全程打同源，看不到 Railway 網域。

後台 SPA（第二個 Pages 專案）

設定值
Build commandnpm --prefix admin ci && npm --prefix admin run build:only
Output directoryadmin/dist
環境變數Supabase 三件；ADMIN_API_BASE 留空（預設同源 /api，由這個專案的 Pages Function 轉發 — 所以這個專案也要設 API_ORIGIN + EDGE_SECRET）
SPA 路由需要 admin/dist/_redirects 寫 /* /index.html 200 — 若檔案不存在請在 repo 補上。

Deploy Hook（發布迴路）

  • 前台 Pages 專案 → Settings → Builds → Add deploy hook → 建立，拿 URL。Cloudflare 介面若顯示 Builds & deployments，仍是在同一個 Builds 區塊。
  • 回填 Railway 的 CF_DEPLOY_HOOK_URL。tools/publish 的流程：先在本地 render dist/ 做預檢（失敗即中止、保留舊 dist）→ 成功後 POST hook，讓 Pages 從 Git 分支重建 — Pages build 內的 make site 會用 production DB 重新 render，整個流程不上傳 dist。
  • 後台的內容「發布」按鈕只把 DB 草稿標記為 published，不會自動觸發上述流程 — 內容要上線，由 CI 或人工執行 go run ./server/tools/publish，或直接 push 觸發 Git build。

網域綁定 + 邊緣驗證 Cloudflare DNS

  • 網域 DNS 託管到 Cloudflare（Registrar 買或把 nameserver 指過來）。
  • 前台網域：前台 Pages 專案 → Custom domains → 綁 你的網域。
  • 後台網域（選配）：後台 Pages 專案 → Custom domains → 綁 admin.你的網域；不綁就用 *.pages.dev 也可以。
  • 不需要 api. 子網域、不需要 Transform Rule — repo 根的 functions/api/[[path]].js 已把 /api/* 轉發到 API_ORIGIN 並注入 EDGE_SECRET。
  • 驗證邊緣閉環：curl https://你的網域/api/products 回 200（經 Function 注入 secret）；curl https://xxx.up.railway.app/api/products 直打回 403 — 這代表 Railway origin 只接受經過 Pages 的流量。
EDGE_SECRET 輪換零中斷三步驟：① Railway 設 EDGE_SECRET_PREVIOUSSECRET = 舊值、EDGE_SECRET = 新值，重新部署 — origin 過渡期同時接受新舊兩值，Pages 還在送舊值也不受影響 → ② 兩個 Pages 專案的 EDGE_SECRET 改成新值並重新部署 → ③ 確認邊緣全送新值後，移除 Railway 的 EDGE_SECRET_PREVIOUS 並重新部署。/healthz 已豁免，Railway healthcheck 不受影響。注意：EDGE_SECRET_PREVIOUS 只為輪換窗口存在，完成後務必移除 — 留著等於兩組憑證長期有效。
