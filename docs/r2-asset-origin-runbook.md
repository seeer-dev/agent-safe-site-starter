# R2 Asset-Origin Headers Runbook

## Status: NOT live-applied

This runbook documents the required external Cloudflare configuration for
public asset-origin headers. The Go renderer generates `dist/_headers`
for the Cloudflare Pages site, but R2-served assets (verified product
images) are on a **separate origin** (R2 custom domain or `r2.dev`) and
are NOT covered by the Pages `_headers` file. The operator must live
HEAD/GET verify that `X-Content-Type-Options: nosniff` appears on R2
responses; only if it is missing should a Response Header Transform Rule
or Managed Transform be added in the Cloudflare dashboard.

**No live R2 or Cloudflare configuration has been applied.** This is a
code-level runbook for the operator who performs the live setup.

## 1. Pages `_headers` (generated by Go renderer)

The Go renderer (`server/internal/render/headers.go`) generates
`dist/_headers` inside the staging directory during every atomic render.
This file is promoted to `dist/` with the rest of the static output and
served by Cloudflare Pages.

Contents:
- `X-Content-Type-Options: nosniff`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `X-Frame-Options: DENY`
- `Content-Security-Policy` with strict allowlist:
  - `default-src 'self'`
  - `script-src 'self'`
  - `style-src 'self' 'unsafe-inline'` (Vue runtime inline styles)
  - `img-src 'self' data: <R2_PUBLIC_BASE_URL origin>` (when valid)
  - `connect-src 'self' <PUBLIC_API_BASE origin>` (when valid)
  - `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`

Empty origins are omitted from the CSP (local dev, no external
CDN/API). Non-empty but invalid origins (newline, non-http(s) scheme,
missing host) cause `buildHeaders` to return an error -- `renderToStaging`
fails-closed and preserves the last-known-good `dist/` with its previous
`_headers`.

Reference: https://developers.cloudflare.com/pages/configuration/headers/

## 2. R2 custom domain -- nosniff verification (REQUIRED)

R2 public buckets serve objects via a custom domain (e.g.
`cdn.example.com`) or the Cloudflare-managed `r2.dev` subdomain. The
Pages `_headers` file does NOT apply to R2-served assets -- R2 has its
own response headers. The Go backend sets `ContentType` and
`Cache-Control: public, max-age=31536000, immutable` on verified
objects via `CopyObject` with `MetadataDirectiveReplace` (see
`server/internal/platform/storage/r2.go`), but `X-Content-Type-Options:
nosniff` is not set by `CopyObject` -- it is an HTTP response header
controlled by the R2/Cloudflare serving layer, not object metadata.

### Deployment acceptance: HEAD/GET verification

After deploying the R2 custom domain, the operator MUST verify that
`X-Content-Type-Options: nosniff` appears on R2 responses:

```
curl -I https://cdn.example.com/verified/product-images/<sha256>.jpg
```

If `X-Content-Type-Options: nosniff` is NOT present on the R2 response,
the operator must add it via one of:

1. **Response Header Transform Rule** (custom domain only -- not
   available on `r2.dev`):
   - Cloudflare Dashboard -> your domain -> Rules -> Transform Rules
   - Create a Response Header Transform Rule
   - When: matches the R2 custom domain (e.g. `cdn.example.com/*`)
   - Action: Set static header `X-Content-Type-Options` = `nosniff`
   - (Optional) Also set `Referrer-Policy: strict-origin-when-cross-origin`

2. **"Add security headers" Managed Transform** (custom domain only):
   - Adds `x-content-type-options: nosniff` among other security headers
   - Can be used if the other headers it adds are acceptable

References:
- https://developers.cloudflare.com/rules/transform/response-header-modification/
- https://developers.cloudflare.com/rules/transform/managed-transforms/reference/

### Why nosniff matters

The CSP `img-src` allows the R2 origin, so browsers can load product
images from R2. Without `X-Content-Type-Options: nosniff` on the R2
response, a browser may MIME-sniff the response and execute content as
a different type. The `CopyObject` sets the correct `ContentType`, but
`nosniff` is defense-in-depth -- it tells the browser to trust the
`Content-Type` header and not sniff.

## 3. r2.dev -- non-production only

The Cloudflare-managed `r2.dev` subdomain is intended for development
and testing only. It is rate-limited and does not support custom
headers, WAF rules, caching, or Bot Management.

- **Do NOT use `r2.dev` in production.** Set `R2_PUBLIC_BASE_URL` to
  the custom domain (e.g. `https://cdn.example.com`) in production.
- For local development, `r2.dev` or an empty `R2_PUBLIC_BASE_URL` is
  acceptable (the CSP omits the R2 origin when empty).

Reference: https://developers.cloudflare.com/r2/buckets/public-buckets/

## 4. Cache-Control on verified objects

The Go backend sets `Cache-Control: public, max-age=31536000, immutable`
on verified product images via `CopyObject`. This is correct because
verified object keys are content-addressed (SHA256 of the image bytes) --
the object at a given key is immutable and will never change.

- `public`: allows CDN caches to cache the response
- `max-age=31536000`: 1 year
- `immutable`: browsers skip revalidation on reload

### Live cache behavior verification (REQUIRED)

Per Cloudflare docs, R2 custom domains use Cloudflare Cache, but "by
default, only certain file types are cached." The default cached file
extensions include JPG, JPEG, PNG, GIF, WEBP, and AVIF -- so verified
product images (JPEG/PNG/GIF) should be cached by default. However,
this must be verified live after deploying the R2 custom domain:

1. Verify the `Cache-Control` header appears on the R2 response:
   ```
   curl -I https://cdn.example.com/verified/product-images/<sha256>.jpg
   ```
2. Verify Cloudflare CDN caching behavior (e.g. `cf-cache-status` header):
   ```
   curl -I https://cdn.example.com/verified/product-images/<sha256>.jpg
   ```
   - `cf-cache-status: HIT` indicates the CDN is caching the object
   - `cf-cache-status: MISS` on first request, then `HIT` on subsequent
   - If caching is not working as expected, create a Cache Rule with
     "Cache Everything" for the R2 custom domain path

Reference: https://developers.cloudflare.com/r2/buckets/public-buckets/#caching

Do NOT assume the `Cache-Control` header alone guarantees CDN caching
without live verification -- Cloudflare's default cache behavior only
covers certain file extensions, and Cache Rules may be needed depending
on the deployment configuration.

## 5. Object lifecycle and database-aware media GC

### Temporary uploads: R2 lifecycle rule

Configure exactly one expiration rule for the `uploads/` prefix with an age of
one day. Do not include `verified/` in this rule. Cloudflare evaluates object
lifecycle rules at bucket level, supports prefix filters, and may remove an
expired object up to roughly 24 hours after its expiration time.

Dashboard:

1. R2 > select the bucket > Settings > Object lifecycle rules.
2. Add a rule named `expire-temporary-uploads`.
3. Scope the rule to prefix `uploads/`.
4. Expire objects after 1 day.
5. Save, then verify the displayed prefix and duration before enabling it.

Wrangler equivalent (verify the installed Wrangler syntax with `--help` before
applying because the CLI surface is versioned):

```text
npx wrangler r2 bucket lifecycle add <bucket> expire-temporary-uploads uploads/ --expire-days 1
npx wrangler r2 bucket lifecycle list <bucket>
```

Never use an age-only bucket-wide rule. A bucket-wide rule would eventually
delete active product images because R2 cannot see database references.

Cloudflare reference:
https://developers.cloudflare.com/r2/buckets/object-lifecycles/

### Verified media: Go GC tool

Verified media follows database references, not an R2 lifecycle rule:

- Any `product_images` row protects the canonical asset indefinitely.
- Removing the final association starts a new 7-day grace period.
- Re-verifying the object renews that grace period.
- A stale `verifying` reservation becomes eligible after 24 hours.
- GC claims the database row and creates `media_gc_jobs` atomically before it
  deletes R2 bytes. A failed provider deletion remains queued for retry.
- Output contains counts only and does not log object keys or user identifiers.

Preview without mutation:

```text
go run ./server/tools/media-gc
```

Apply one bounded batch:

```text
go run ./server/tools/media-gc --apply --batch 100
```

Run the apply command daily from the deployment platform scheduler. Treat a
non-zero exit caused by provider failures as retryable: the durable jobs remain
in `media_gc_jobs` and the next run continues them. Do not run two schedulers
for the same database unless PostgreSQL is the active driver; SQLite is intended
for one application process.

Before the first production apply:

1. Apply migration 015 to the same database used by the application.
2. Run the preview and record its count-only output.
3. Confirm the R2 credentials point at the same bucket as media verification.
4. Run `--apply --batch 1`, verify the deletion result, then enable the daily
   bounded batch.
